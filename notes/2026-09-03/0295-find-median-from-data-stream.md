# 295. 数据流的中位数 —— 复盘笔记

## 当前解答与核心思路

当前 `solution.cpp` 保留用户自己完成的双堆实现：使用 `lsize`、`rsize` 记录数量，并分别处理首次插入、右堆为空和两个堆都非空的情况。本次只删除未使用的 `largerMid`，整理注释与格式，没有用下方模板覆盖原算法。

题目目录同时保留以下学习版本，旧文件内容没有修改：

- `solution.cpp`：当前解答，也是 `test.cpp` 默认包含并验证的版本。
- `solution_v2.cpp`：用户保留的双堆初版备份，仍包含未使用的 `largerMid`。
- `solution copy.cpp`：每次添加后全量排序的早期版本，用于对照性能问题，不是当前测试入口。

不需要将所有元素完全排序，只需要把数据分成大小两半：

- `maxHeap` 是大顶堆，保存较小的一半，堆顶是这一半的最大值。
- `minHeap` 是小顶堆，保存较大的一半，堆顶是这一半的最小值。

每次添加完成后，维持以下规则：

1. 左半边所有元素都不大于右半边所有元素；两边非空时，可通过 `maxHeap.top() <= minHeap.top()` 检查边界。
2. 左堆与右堆一样大，或者左堆多一个元素。
3. 所有加入的数据都只保存一份；每次 `addNum` 后，两堆实际元素总数恰好增加 1。
4. 在当前手动计数版本中，`lsize == maxHeap.size()`，`rsize == minHeap.size()`。

因此，奇数个元素时返回大顶堆顶；偶数个元素时返回两个堆顶的平均数。题目保证查询前至少已添加一个元素。

## 学习过程中的问题

### 1. 每插入一个数就重新排序，造成性能瓶颈

最初使用 `vector` 保存数据，每次 `push_back` 后调用 `sort`。中位数的计算是正确的，但已有 k 个数时，一次插入会重新排序 k 个元素，时间为 O(k log k)。

累计添加 n 个元素的最坏总时间为 O(n² log n)，而不是 O(n log n)。本地测试只在全部结束后输出成功，大规模输入下会长时间没有输出。

双堆只调整局部顺序，每次添加需要常数次入堆、出堆，将 `addNum` 降为 O(log n)。

### 2. 手动计数没有更新，导致对空堆调用 top

早期版本在首次入堆的分支中没有执行 `lsize++`，所以后续数字仍然进入“左堆为空”的分支。实际左堆已有数据，但记录的 `lsize`、`rsize` 都是 0，右堆为空。

查询时程序没有进入“左边多一个”的分支，继续读取 `minHeap.top()`，触发 `Assertion '!this->empty()' failed`。

这不是标准库本身出错。`priority_queue::top()` 要求堆非空；报错中的 `greater<int>` 对应这里的小顶堆。修复时应让计数和真实状态一致，不能仅通过跳过报错的读取来掩盖状态错误。

### 3. 第二个数不能无条件放到右堆

例如依次添加 `[5, 1, 2]`，每一步的正确中位数是 `[5, 3, 2]`。

添加第二个数 1 后，应当是左堆保存 1、右堆保存 5。如果反过来，两个堆顶的平均数仍然是 3，因此第二步可能通过；但后续插入时会破坏中位数计算。

本次还遇到递减序列 `[6, 5, 4]` 的第三步失败，正确中位数应为 5。检查两个堆的内容时，不能只检查数量，还要检查左右的大小关系。

### 4. if/else 外残留一次 push，重复保存了数据

修正第二个数的分配后，曾在 `if/else` 内完成插入，又在分支后无条件执行一次 `minHeap.push(num)`。部分路径还重复执行了 `rsize++`。

对于当时的 `[1, 2, 3, 4]`，实际保存的数据如下。表中的集合只表示元素内容，不表示堆的内部数组顺序。

| 操作 | 大顶堆内容 | 小顶堆内容 | 记录的 lsize / rsize |
|---|---|---|---|
| 添加 1 | {1} | {} | 1 / 0 |
| 添加 2 | {1} | {2, 2} | 1 / 1 |
| 添加 3 | {1, 2} | {2, 3} | 2 / 1 |
| 添加 4 | {1, 2} | {2, 3, 4} | 2 / 2 |

错误从第二次插入就发生了，但第二、第三次查询碰巧仍然正确。第四次查询时，两个堆顶都是 2，所以返回 2，而不是期望的 2.5。

这次的错误不是整数除法，而是数据重复和计数失真。调试时应从第一个状态异常的位置开始检查，而不只是检查最后的返回公式。

在右堆为空的分支中，两条路径最终都应该使左堆数量不变、右堆数量增加 1：

- 新数较小：先加入左堆，再将左堆最大的数移到右堆。
- 新数较大：直接加入右堆。

不能在这两条路径之外再重复插入新数。

## 为什么自己的实现比较繁杂

当前版本正确，但存在重复维护和重复分支：

- 两个堆本来就能通过 `size()` 返回数量，额外的 `lsize`、`rsize` 需要同步维护。
- 首次插入、第二次插入单独处理，增加了初始化分支。
- 按数量判断和按数值判断相互嵌套，同样的堆顶移动逻辑散落在多个位置。

更清晰的组织方式是分开两件事：先按数值决定新数属于哪边，再统一调整数量。这改变的是代码组织方式，不是双堆算法的复杂度。

## 推荐模板：先分配，再平衡

以下模板供复习对照，当前提交的 `solution.cpp` 仍然保留用户自己的分支和计数写法。

```cpp
#include <queue>
#include <vector>
#include <functional>

using namespace std;

class MedianFinder {
private:
    // 较小的一半：堆顶是这一半的最大值
    priority_queue<int> maxHeap;
    // 较大的一半：堆顶是这一半的最小值
    priority_queue<int, vector<int>, greater<int>> minHeap;

public:
    MedianFinder() {
        // 两个堆默认就是空的
    }

    void addNum(int num) {
        // 先按数值分配
        if (maxHeap.empty() || num <= maxHeap.top()) {
            maxHeap.push(num);
        } else {
            minHeap.push(num);
        }

        // 再按数量平衡
        if (maxHeap.size() > minHeap.size() + 1) {
            minHeap.push(maxHeap.top());
            maxHeap.pop();
        } else if (minHeap.size() > maxHeap.size()) {
            maxHeap.push(minHeap.top());
            minHeap.pop();
        }
    }

    double findMedian() {
        if (maxHeap.size() > minHeap.size()) {
            return maxHeap.top();
        }
        return (static_cast<double>(maxHeap.top())
                + minHeap.top()) / 2.0;
    }
};
```

### 模板中的几个关键点

- `priority_queue<int>` 默认是大顶堆；使用 `greater<int>` 时是小顶堆。
- `||` 从左向右短路求值：左堆为空时，不会访问 `maxHeap.top()`。
- 新数不大于左堆最大值时放左边，否则放右边；右堆内部无需完全有序，新数也无需大于右堆所有元素。
- 左边太多时移动左边最大值，右边太多时移动右边最小值，移动边界元素不会破坏左右大小关系。
- 每次只添加一个数，原本已经平衡，所以最多搬动一个元素即可恢复数量规则，用 `if/else if` 就足够。
- 不对两个无符号的 `size()` 结果直接做减法，使用大小比较，避免数量相减时的无符号下溢。
- 模板在相加前转换为 double，并除以 `2.0`。当前题目中两个堆顶之和在 int 范围内，用户原先先求和再转 double 的写法也能正确处理本题；扩大数值范围时应特别注意求和溢出。

例如添加 `[6, 5]`：6 先进入左堆，5 也先进入左堆；左边有两个、右边为空，于是将最大的 6 移到右堆，自然得到左边 {5}、右边 {6}，不需要第二次插入的专门分支。

## 复杂度

- `addNum`：O(log n)，每次只执行常数次堆操作。
- `findMedian`：O(1)，只读取数量和堆顶。
- 额外空间：O(n)，所有输入数字保存在两个堆中。
